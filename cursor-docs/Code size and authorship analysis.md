# Code Size and Authorship Analysis

This document summarizes how much backend and frontend code exists in this
repository and whether it is possible to determine if the code was written by AI
or by humans.

It covers only:

- `api/`
- `frontend/`

It does not cover `mobile/`, `home/`, generated Cursor documentation, or the
full repository.

There is no reliable way to prove from this repository alone whether the code

- No clear "Generated by ChatGPT/Copilot/Cursor" markers were found in the

  but they cannot prove AI authorship.

## Can we determine whether the code was written by AI?

Not reliably.

There is no dependable method that can look at a codebase and prove:

```text
This was written by AI.
```

or:

```text
This was written by humans.
```

without stronger external evidence.

## What evidence was checked?

Searches were performed for obvious markers such as:

- ChatGPT

- Cursor
- AI-generated
- generated by AI
- CodeBuddy
- Qwen

No clear "this source code was generated by AI" markers were found in backend or
frontend source files during this review.

### 2. AI/assistant tool configuration

The repository contains assistant-related configuration or summary files:

```text

```

What this means:

- Some AI/code-assistant tooling was configured or used around the project.
- It does not prove that the application code was generated by AI.
- It does not prove that the application code was not generated by AI.

These files are evidence of tool presence, not definitive authorship.

### 3. Git author history

For commits touching `api/` and `frontend/`, git history mostly shows named
human-looking authors. The largest author count observed was:

```text
Ibrahima G. Coulibaly <ibracool99@gmail.com>
```

Other named authors also appear.

This suggests the repository has a normal human contributor history.

But this is not proof of human-only authorship because:

- a human can commit AI-generated code
- an AI-assisted patch can be committed under a human name
- a bot can use a human-looking author name
- historical commits do not reveal how code was produced

### 4. Code style and architecture

The codebase has signs of long-term human product evolution:

- many modules
- inconsistent naming in places
- technical debt
- feature gating
- old and new patterns mixed together
- large contexts/controllers
- multiple contributors

These patterns are common in human-maintained production systems.

However, AI-generated code can also contain inconsistencies, and humans can
write repetitive or boilerplate-heavy code. Style is not reliable evidence.

## Why AI detection is hard for code

AI authorship detection is much harder for code than for plain text.

Reasons:

1. Code has strong conventions.
   - Many developers write similar controller/service/model patterns.
   - Frameworks encourage repeated structures.

2. Boilerplate looks AI-like even when human-written.
   - DTOs, reducers, translation objects, CRUD screens, and mappings repeat.

3. AI-assisted code can be heavily edited by humans.
   - The final result may no longer look AI-generated.

4. Human code can be generated from tools.
   - IDE refactors, code generators, MapStruct, OpenAPI clients, migrations,
     and templates all create generated-looking code.

5. Commit history records who committed, not who authored every line.

6. There is no cryptographic authorship marker in normal source files.

## What would be needed to prove AI authorship?

Stronger evidence would include:

- commits explicitly saying code was generated by AI
- pull request descriptions mentioning AI generation
- prompt logs or agent transcripts
- generated-code headers inserted by AI tools
- CI metadata from an AI coding agent
- issue comments where maintainers state AI was used
- exact before/after patches from an AI assistant
- vendor disclosure from project maintainers

Without evidence like that, any claim would be speculation.

## What can be concluded for this project?

Reasonable conclusions:

1. The backend and frontend are large enough that they represent substantial
   product work.
2. The repository has a normal-looking human contributor history.
3. AI tooling configuration exists in the repository.
4. No obvious "AI generated this code" source headers were found.
5. It is not possible to confidently determine AI vs human authorship from the
   repository alone.

Unreasonable conclusions:

- "This code was definitely written by AI."
- "This code was definitely written only by humans."
- "Because there is Qwen/CodeBuddy config, the project is AI-generated."
- "Because git authors are humans, AI was not used."

## Practical way to think about it

For adoption or maintenance, the more useful question is not:

```text
Was this written by AI?
```

The more useful questions are:

```text
Is the code understandable?
Is it maintainable?
Can the team test it?
Can the team safely change it?
Does it implement valuable CMMS behavior?
Are licensing and product limits acceptable?
```

Those questions can be answered more reliably than authorship.

## Recommended due diligence

If you need confidence before adopting this project:

1. Review important modules manually.
2. Run the application locally.
3. Add tests around critical flows.
4. Check security-sensitive code.
5. Review licensing gates.
6. Ask maintainers directly whether AI tools were used.
7. Review pull requests and issue history if available.
8. Treat AI-assisted code the same as human code: inspect, test, and maintain it.
